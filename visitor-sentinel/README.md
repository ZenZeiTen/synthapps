# Visitor Sentinel

A WordPress plugin for visitor analytics with **IP address tracking**, **page activity tracking**
and **fraudulent click detection** for paid ad clicks and on-site ads.

| Path | What it is |
|---|---|
| [visitor-sentinel/](visitor-sentinel/) | The plugin. Zip this folder to install it. |
| [tests/](tests/) | Unit and integration tests, a browser end-to-end test, and a real-WordPress smoke test |

Installable zips are attached to the
[Visitor Sentinel releases](https://github.com/ZenZeiTen/synthapps/releases?q=visitor-sentinel).
To publish one, raise `Version` in `visitor-sentinel.php`, update [RELEASE_NOTES.md](RELEASE_NOTES.md),
then on the Actions page run the **Visitor Sentinel** workflow on `main` with **Publish a release**
ticked. It runs every test, builds `visitor-sentinel-<version>.zip` and publishes release
`visitor-sentinel-v<version>`. Pushing a tag with that name does the same.

## What it does

**IP address tracking.** Each visitor's IP, country (from Cloudflare or any geolocation service
through the `vsen_country` filter), browser, OS and device. The real client address is resolved
behind Cloudflare and reverse proxies, and forwarded-for headers count only from proxies you trust.
IPs can be stored in full, masked (`203.0.113.0`) or not at all. Detection and blocking still work
because they match a keyed hash of the full address.

**Page activity tracking.** Pageviews, sessions, entry and exit pages, referrers, UTM campaigns,
time on page, visible time, scroll depth, interactions, outbound links, downloads and
`data-vsen-track` elements. It includes a live "who is on the site now" panel and a per-visitor
activity timeline. The tracker is one script (about 12 KB unminified) with no dependencies and no cookies. It reports
through the REST API, so it works behind full-page caches.

**Fraudulent click detection.** Paid landings (`gclid`, `gbraid`, `wbraid`, `msclkid`, `ttclid`,
`li_fat_id`, `twclid`, `ScCid`, `yclid`, `rdt_cid`, `fbclid` with a paid `utm_medium`, or a paid
`utm_medium` alone) and clicks on ad units are scored from 0 to 100. Clicks inside ad iframes
such as AdSense count too. The score comes from 16 rules:

| Rule | Points |
|---|---|
| Bot, crawler or HTTP-library user agent | 60 |
| Headless browser, `navigator.webdriver`, zero-size screen | 50 |
| Click event generated by script (`isTrusted` false) | 45 |
| Server saw the ad landing, no browser ever ran the page | 40 |
| IP in a suspicious network you listed | 40 |
| Ad click ID reused from another IP | 35 |
| IP already blocked | 30 |
| More ad clicks per IP per hour than allowed (+8 each, up to +24) | 30 |
| Same ad clicked again within 10 minutes | 30 |
| More ad clicks per IP per 24 hours than allowed | 25 |
| On-site ad clicked within 800 ms of page load | 25 |
| Paid visitor left within 3 s without interacting | 25 |
| No mouse, touch, key or scroll activity before an on-site ad click | 20 |
| Five or more visitor IDs on one IP in 24 hours (cleared storage) | 20 |
| IP hit the tracker rate limit | 20 |
| No user agent or no Accept-Language header | 15 |

Sensitivity scales the total (×0.75, ×1, ×1.25). A score of 40 or more is suspicious, and 70 or
more is fraudulent. A score is revised when engagement arrives and finalized after 15 minutes by
the hourly cron.

**Protection.** Automatic blocking at a threshold, with expiry. Blocked IPs are recorded only, see
the site without ads (the default, and it works on cached pages), or get a 403. Administrators,
the login page and search or ad crawlers are never blocked automatically. The blocklist exports
in Google Ads "IP exclusions" format. An hourly email digest reports new fraud.

## Limits worth knowing

- No plugin can stop an ad network from charging for a click that already happened. This plugin
  finds the click, hides ads from its source and gives you evidence and an IP exclusion list.
- Clicks inside third-party ad iframes cannot be seen directly. They are inferred from the page
  losing focus while the pointer is over the ad, which is the standard method and can miss or
  over-count in edge cases.
- Country needs Cloudflare or a geolocation hook. No geo database is bundled.
- The "no JavaScript" signal needs the uncached page for ad landings. Most page caches bypass
  URLs that carry click IDs, but check yours.
- Without a persistent object cache, the rate limiter stores short-lived transients in the
  options table.
- WordPress.org hosts an unrelated plugin in a folder with the same name. The plugin opts out of
  WordPress.org updates (`Update URI: false`, and it drops any cached offer), so updates come only
  from uploading a newer zip with **Replace current with uploaded**.

## Tests

```bash
php tests/run.php
```

The test suite has 54 unit and integration tests. They run the real plugin code against a
SQLite-backed `$wpdb` and a small stub of WordPress, because every query is written to run on both
MySQL and SQLite. Any PHP warning or notice fails a test.

```bash
node tests/e2e/browser.test.cjs
```

This runs the real `tracker.js` in Chromium (Playwright) against the real PHP endpoint. A
person-like session stays clean. An automated browser that clicks an ad by script is scored as
fraud and blocked, and has its ads hidden on the same page and the next one.

```bash
DB_HOST=127.0.0.1 DB_USER=root DB_PASS=root bash tests/wordpress-smoke.sh
```

This installs WordPress on MySQL with WP-CLI, activates the plugin, records a server-side and a
browser-reported ad landing, runs cron, and loads every admin screen as an administrator. The
[CI workflow](../.github/workflows/visitor-sentinel.yml) runs all three, with the unit tests on
PHP 7.4 to 8.3.
